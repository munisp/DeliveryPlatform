# Real Dispatch Export Signature Authentication Plan

## Purpose and boundary

The current `source_export_digest` detects accidental or unilateral changes only when the manifest and export are held in a trusted immutable channel. It does **not** authenticate the data owner: an attacker who can replace both the JSONL export and detached manifest can calculate a new matching SHA-256 digest.

This plan upgrades the export protocol to cryptographic **data-owner authentication**. It does not change the offline evaluator's non-authoritative boundary. Even a verified historical export can produce only shadow-evaluation evidence; it cannot execute payments, change a vehicle state, alter inventory, or activate a dispatch policy.

## Target protocol

Use **Ed25519** signatures. The data owner signs a canonical manifest payload in a hardware-backed key-management service or HSM. The evaluator verifies the signature using an allowlisted public key held in a locally managed trust store. Private keys never appear in exports, source control, shell history, evaluator configuration, or audit logs.

| Element | Required value |
|---|---|
| `signature_schema_version` | `1` |
| `algorithm` | Exact string `Ed25519` |
| `key_id` | Immutable opaque ID referencing an allowlisted public key, for example `dispatch-data-owner-2026-q3` |
| `signed_at` | ISO-8601 UTC timestamp generated by the signing authority |
| `signature` | Base64url-without-padding Ed25519 signature bytes |
| `signed_payload` | Canonical manifest payload below; the signature object itself is excluded |
| `source_export_digest` | Existing SHA-256 canonical JSONL digest, included in the signed payload |

The detached manifest obtains a `signature` object. Its public-key material is intentionally excluded; a manifest must not be able to nominate its own trust anchor.

```json
{
  "manifest_schema_version": 2,
  "record_schema_version": 1,
  "source_export_digest": "<64 lowercase hex characters>",
  "domain": "dispatch_offer_ranking",
  "source_system": "append-only-dispatch-log",
  "exported_at": "2026-09-10T12:05:00+00:00",
  "reward_definition_version": "dispatch-v1",
  "propensity_logger_version": "policy-v1",
  "append_only_attested": true,
  "propensities_recorded_at_decision_time": true,
  "direct_identifiers_removed": true,
  "location_traces_removed": true,
  "signature": {
    "signature_schema_version": 1,
    "algorithm": "Ed25519",
    "key_id": "dispatch-data-owner-2026-q3",
    "signed_at": "2026-09-10T12:05:03+00:00",
    "signature": "<base64url Ed25519 signature>"
  }
}
```

## Exact signed bytes

The signing payload must be deterministic across all producer and verifier implementations. Construct it by copying the full manifest, removing `signature`, then serializing with the existing canonical JSON convention:

```text
manifest_without_signature = manifest with the `signature` member removed
canonical_manifest = json.dumps(
    manifest_without_signature,
    sort_keys=True,
    separators=(",", ":"),
    ensure_ascii=True,
).encode("utf-8")

signed_bytes = (
    b"deliveryplatform.real-dispatch-export.manifest.v1\\x00"
    + canonical_manifest
)
```

The domain-separation prefix prevents a valid signature for another payload type from being accepted as a dispatch-export manifest. The signed manifest binds the source digest, domain, source system, export timestamp, schema versions, redaction attestations, and reward/propensity definition versions together. The existing parser continues to recompute the canonical JSONL digest and compare it to the signed `source_export_digest`.

> Do not sign only the SHA-256 digest. Signing the complete canonical manifest also authenticates the contextual declarations needed to interpret the export safely.

## Fail-closed verifier sequence

The verifier must complete the following steps in order. Any failed step raises `PolicyEvaluationError` and yields no records.

| Order | Verification | Failure condition |
|---:|---|---|
| 1 | Parse the manifest as a JSON object. | Invalid JSON, duplicate-key-unsafe parser, or non-object input. |
| 2 | Enforce manifest schema version `2` and exact signature object fields. | Missing, extra/unknown critical, or unsupported fields. |
| 3 | Enforce algorithm `Ed25519`, non-empty `key_id`, strict base64url decoding, and a 64-byte decoded signature. | Algorithm substitution, malformed encoding, or wrong signature length. |
| 4 | Resolve `key_id` only from an evaluator-controlled trust store. | Unknown, revoked, expired, inactive, wrong owner/scope, or wrong environment key. |
| 5 | Enforce signing-time and export-time policy. | Non-UTC time, excessive future skew, signing time after export time, or export older than retained governance window. |
| 6 | Reconstruct `signed_bytes` exactly and call Ed25519 verification. | Invalid signature. |
| 7 | Recompute the canonical JSONL digest and compare it with the signed manifest digest and every record digest. | Any record alteration, order change, insertion, deletion, or digest mismatch. |
| 8 | Run existing privacy, schema, timestamp, duplicate, domain, action, propensity, and reward gates. | Any pre-existing parser/evaluator rejection. |
| 9 | Emit an audit event with export digest, manifest digest, verified `key_id`, verification time, and verification result. | Audit write failure; do not report a successful evaluation. |

Signature validation must occur before the parser returns records. Signature verification must not perform network key discovery, follow URLs in the manifest, invoke a dynamic plugin, or accept an embedded public key.

## Key-management and trust-store design

The signing service should use a cloud KMS, on-premises HSM, or another key service that supports Ed25519 without exporting private key material. It should expose a narrowly scoped signing identity for approved export jobs only. The job sends the exact `signed_bytes` to the signer; it receives only a signature.

The evaluator trust store is version-controlled configuration or a separately deployed, access-controlled bundle. Each key entry must include its `key_id`, base64-encoded 32-byte Ed25519 public key, owner identity, allowed source systems, allowed domains, activation time, expiry time, revocation status, and environment. The verifier must require all scope claims to match the manifest.

Key rotation is additive: publish a new trust-store key before a producer begins signing with it; allow the predecessor only through a bounded overlap period; then mark it inactive and subsequently revoked. Never silently replace public key material under an existing `key_id`. A key-compromise response revokes the key, blocks all exports signed by it, records the incident, and requires a new export signed by an active key.

## Required code changes

| Component | Change |
|---|---|
| `real_dispatch_export_parser.py` | Add manifest-v2 signature validation before `_read_canonical_records`; keep v1 behavior available only for explicitly non-historical local fixtures, never for a real-evidence command. |
| New `real_dispatch_export_signature.py` | Hold strict canonical-manifest construction, base64url decoding, Ed25519 verification, trust-store loading, time checks, and structured error handling. |
| Evaluator CLI | Replace the optional manifest behavior for real-evidence mode with `--provenance-manifest` plus `--trust-store`; require both for a historical-evidence evaluation. |
| Audit writer | Include `source_export_digest`, `manifest_digest`, `verified_key_id`, signature schema, and verification timestamp in the hash-chained audit entry. Never include signature bytes or secret material. |
| CI | Pin the cryptographic dependency, generate ephemeral test-only Ed25519 keys in test setup, and exercise valid, unknown-key, revoked-key, bad-signature, wrong-algorithm, malformed-signature, expired-key, wrong-domain, and key-rotation cases. |

Use a mature, pinned cryptography implementation such as Python `cryptography`'s Ed25519 API. Do not implement Ed25519 primitives, base64 decoding, or signature comparison manually.

## Rollout and downgrade resistance

1. Introduce manifest schema version `2` and signature verification in shadow-only mode, while continuing to reject untrusted real exports.
2. Register and scope public keys, perform signer/verifier interoperability tests, and retain immutable fixtures that are clearly labeled test-only.
3. Require a successful signature audit event before an export is eligible for any offline policy estimate labeled as real historical evidence.
4. Forbid manifest version fallback when a caller declares historical evidence. A v1 unsigned manifest must not be accepted through the signed-evidence command path.
5. Monitor signature-verification failures, unknown key IDs, near-expiry keys, and time-skew failures. Investigate and remediate before accepting a replacement export.
6. Keep model/governance approval separate: verified provenance proves origin and integrity, not causal validity, fairness, policy fitness, or authorization to deploy.

## Acceptance tests

The implementation is ready to claim authenticated provenance only after tests prove all of the following.

| Scenario | Expected result |
|---|---|
| Active scoped key signs the exact canonical manifest. | Parser accepts the export if all existing gates pass. |
| JSONL record is modified, removed, added, or reordered after signing. | Canonical source digest comparison fails. |
| Manifest source digest, domain, redaction attestation, or reward definition is modified after signing. | Ed25519 verification fails. |
| Signature is modified, malformed, empty, or signed over a different payload. | Verification fails. |
| Key ID is unknown, revoked, expired, out of scope, or environment-mismatched. | Trust-store resolution fails. |
| Algorithm is changed or omitted. | Algorithm allowlist check fails. |
| Producer attempts to embed a public key in the manifest. | Schema rejects the unrecognized trust-anchor field. |
| A historical-evidence command supplies a v1 unsigned manifest. | Downgrade-protection check fails. |
| All cryptographic checks pass but policy/privacy gates fail. | Parser still rejects the export. |

No synthetic dataset becomes historical evidence through signatures. Test keys and synthetic fixtures establish only parser correctness, never real dispatch provenance or economic uplift.
