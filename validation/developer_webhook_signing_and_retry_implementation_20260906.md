# Developer Webhook Signing, Verification, and Durable Retry Simulation

**Date:** 2026-09-06

**Implementation scope:** Outbound Developer API webhooks and inbound Medusa commerce event verification.

**Evidence scope:** Local loopback transport simulation and disposable PostgreSQL/PostGIS databases only. No external endpoint, staging cluster, DNS record, secret-manager value, customer data, or production database was used.

## Separation of the two cryptographic paths

The platform has two distinct HMAC-SHA-256 paths. The Developer API dispatcher **signs outbound** field-service and commerce notifications sent to a partner endpoint. The Medusa commerce ingress **verifies inbound** raw Medusa event bodies before they can be persisted. They use separate environment mappings and should use separate per-endpoint/per-store secrets.

| Direction | Code | Input signed or verified | Header form | Result |
|---|---|---|---|---|
| DeliveryPlatform → developer endpoint | `server/_core/developerWebhookDispatcher.ts` | Exact UTF-8 JSON request body | `X-Webhook-Signature-256: sha256=<64 lowercase hexadecimal characters>` | The partner can authenticate that the body was generated by a holder of the shared endpoint secret. |
| Medusa store → DeliveryPlatform | `server/_core/medusaCommerce.ts` | Exact raw HTTP body bytes, before reserialization | Accepts `sha256=<64 hexadecimal characters>` or raw 64-character hex | DeliveryPlatform rejects malformed, mismatched, or body-altered signatures with `medusa_event_signature_invalid`. |

> HMAC authenticates a body to parties that hold the shared secret. It does not encrypt the body, and it does not by itself prevent replay. Developer webhook consumers should verify the HMAC against the raw bytes and deduplicate `X-Delivery-Id`; the delivery database retains one delivery per `(webhook_endpoint_id, event_id)`.

## Outbound Developer API signing implementation

### Secret handling and claim boundary

The dispatcher reads `DEVELOPER_WEBHOOK_SECRET_REFS_JSON` as a JSON object mapping a database-held secret reference to a secret value. The database stores only `signing_secret_ref`, never the secret. The parser rejects an invalid JSON object, references that do not match `^[A-Za-z0-9][A-Za-z0-9._:/-]{2,255}$`, and secret values shorter than 32 or longer than 4,096 characters.

Before a network request, the dispatcher calls the database function `developer.claim_webhook_deliveries(limit)`. After migration `0048_developer_webhook_delivery_leases.sql`, each returned record includes the persisted `created_at` value and a random `claim_token`. The token is a durable worker lease: it must be returned to `developer.complete_webhook_delivery` after the attempt, so a stale worker cannot report success or failure for a delivery another worker has re-claimed.

The durable claim function only claims due `pending` or `retrying` deliveries with fewer than 16 attempts. It uses `FOR UPDATE SKIP LOCKED`, increments `attempt_count`, sets state to `retrying`, issues a fresh UUID claim token, and sets a 30-second lease. A `retrying` row with an unexpired lease is not eligible for another claim.

```sql
-- Excerpt from 0048: candidate eligibility
WHERE delivery.state IN ('pending'::developer.webhook_delivery_state,
                         'retrying'::developer.webhook_delivery_state)
  AND delivery.next_attempt_at <= p_now
  AND delivery.attempt_count < 16
  AND (
    delivery.state = 'pending'::developer.webhook_delivery_state
    OR delivery.claim_expires_at IS NULL
    OR delivery.claim_expires_at <= p_now
  )
FOR UPDATE SKIP LOCKED

-- Excerpt from 0048: ownership lease
SET state = 'retrying'::developer.webhook_delivery_state,
    attempt_count = delivery.attempt_count + 1,
    claim_token = gen_random_uuid(),
    claim_expires_at = p_now + interval '30 seconds'
```

### Signed envelope and headers

The dispatcher constructs **one** JSON string and passes the same string both to HMAC and to `fetch`. The stable `created_at` is the persisted delivery creation time rather than the dispatch wall clock, so retries of the same delivery retain the same signed envelope and signature if the payload and secret are unchanged.

```ts
const body = JSON.stringify({
  id: delivery.event_id,
  type: delivery.event_type,
  created_at: new Date(delivery.created_at).toISOString(),
  data: delivery.payload,
});

const signature = createHmac("sha256", secret)
  .update(body)
  .digest("hex");

const response = await fetch(delivery.endpoint_url, {
  method: "POST",
  redirect: "error",
  headers: {
    "Content-Type": "application/json",
    "User-Agent": "DeliveryPlatform-Webhook/1.0",
    "X-Delivery-Id": delivery.delivery_id,
    "X-Event-Id": delivery.event_id,
    "X-Webhook-Signature-256": `sha256=${signature}`,
  },
  body,
  signal: AbortSignal.timeout(10_000),
});
```

Because the HMAC input is `body`, receivers must verify against the raw UTF-8 request bytes. They must **not** parse and reserialize JSON before calculating HMAC; key ordering, whitespace, escaping, or timestamp formatting changes would create a different byte sequence and therefore a different signature.

The dispatcher treats every HTTP 2xx response as successful. A non-2xx response records `endpoint_http_<status>` as the error. A fetch error, including a timeout or a loopback connection reset, records synthetic status `599` and the JavaScript error name. It then passes `delivery_id`, `claim_token`, success, status, and error to the token-bound completion function.

```ts
await db.query(
  `SELECT developer.complete_webhook_delivery($1::uuid,$2::uuid,$3,$4,$5)`,
  [
    delivery.delivery_id,
    delivery.claim_token,
    result.success,
    result.status,
    result.error,
  ],
);
```

## Inbound Medusa signature verification function

The inbound verifier does not deserialize and reserialize its HMAC input. It receives the exact `Buffer` captured from the HTTP request. It trims whitespace from the header, accepts an optional `sha256=` prefix, requires exactly 64 hexadecimal characters, and compares equal-length byte buffers with `timingSafeEqual`.

```ts
export function verifyMedusaWebhookSignature(
  rawBody: Buffer,
  header: string | undefined,
  secret: string,
) {
  const received = `${header ?? ""}`.trim();
  const normalized = received.startsWith("sha256=")
    ? received.slice(7)
    : received;
  if (!/^[a-f0-9]{64}$/i.test(normalized)) return false;

  const expected = createHmac("sha256", secret).update(rawBody).digest();
  const candidate = Buffer.from(normalized, "hex");
  return (
    candidate.length === expected.length && timingSafeEqual(candidate, expected)
  );
}
```

Store IDs are constrained by `^[A-Za-z0-9][A-Za-z0-9._:-]{2,159}$`; each configured Medusa secret must be 32–4,096 characters. The ingress validates the store ID, event ID, allowed event type, and JSON body before looking up the store’s secret and invoking this verifier. It subsequently persists the raw-body SHA-256 digest for idempotency/audit correlation. No secret is persisted in the application database.

## Durable retry and exponential backoff

The durable database function, not the dispatch loop’s 5-second polling interval, determines retry timing. On a failed completion, the state remains `retrying` until attempt 16; the next eligible time is calculated from the already-incremented attempt count:

```sql
next_attempt_at = p_now + make_interval(
  secs => LEAST(3600, 2 ^ v_delivery.attempt_count)
)
```

The initial migration used `2 ^ LEAST(attempt_count, 11)`, which unintentionally capped delays at 2,048 seconds. The forward-only migration `0048_developer_webhook_delivery_leases.sql` corrects the expression to `LEAST(3600, 2 ^ attempt_count)` and adds token-bound ownership leases.

| Failed claim attempt | Delay before next eligibility | State after failure |
|---:|---:|---|
| 1 | 2 seconds | `retrying` |
| 2 | 4 seconds | `retrying` |
| 3 | 8 seconds | `retrying` |
| 4 | 16 seconds | `retrying` |
| 5 | 32 seconds | `retrying` |
| 6 | 64 seconds | `retrying` |
| 7 | 128 seconds | `retrying` |
| 8 | 256 seconds | `retrying` |
| 9 | 512 seconds | `retrying` |
| 10 | 1,024 seconds | `retrying` |
| 11 | 2,048 seconds | `retrying` |
| 12–15 | 3,600 seconds maximum | `retrying` |
| 16 | No further schedule | `dead_letter` |

A completion call must present the active unexpired claim token. A missing, expired, or mismatched token fails with SQLSTATE `55000`; a non-`retrying` row returns its existing state. Successful completion sets `delivered_at`, clears `last_error`, and clears both claim-lease columns. Failed completion records the status/error, clears both claim-lease columns, and schedules the next due time unless the row has reached `dead_letter`.

## Automatically executable retry/backoff simulation

The added executable script is:

```bash
scripts/testing/test-developer-webhook-retry-backoff.sh
```

Run it from the repository root:

```bash
./scripts/testing/test-developer-webhook-retry-backoff.sh
```

The script does not read a database URL or call an external web address. It creates a uniquely named local disposable database; checks that any pre-existing local test roles are non-login and have no privileged memberships; applies migrations `0044`, `0045`, and `0048`; and drops the database automatically in an `EXIT` trap. The placeholder HTTPS endpoint stored in the database is `https://webhook-simulator.invalid/delivery`; it is never contacted.

The test first runs the real TypeScript dispatcher against a `127.0.0.1` receiver that forcibly destroys the connection. The dispatcher classifies that loopback transport fault as a retriable `(success=false, status=599, error="TypeError")` completion. Separate loopback tests also verify the exact HMAC header, successful HTTP 204 completion, and an HTTP 503 retriable completion.

It then invokes the actual PostgreSQL claim and completion functions with controlled timestamps, reproducing the durable result a network failure supplies to the completion boundary. Its assertions cover the following behavior.

| Assertion | How it is tested |
|---|---|
| Exponential delay calculation | It fails one delivery six times and checks the exact 2, 4, 8, 16, 32, and 64 second durable schedules. |
| No premature retry | It tries to claim each delivery at one second before `next_attempt_at` and requires no claim. |
| No simultaneous duplicate claim | It attempts a second claim while the original lease is active and requires no result. |
| Fresh token for each retry | It requires the claim UUID to change across attempts. |
| Stale-worker containment | It tries completion with a random token and requires SQLSTATE `55000`; the active worker can then complete the delivery. |
| Success cleanup | It verifies status `204`, `delivered` state, exact delivery timestamp, and cleared claim token/expiry. |
| Maximum-attempt behavior | It fails a separate delivery through attempts 1–16, checks the 3,600-second cap, verifies `dead_letter` at attempt 16, and confirms it is never claimed again. |
| Evidence cardinality | It verifies exactly two immutable delivery rows were retained for the two simulated events. |

## Deployment compatibility and evidence limits

Migration `0048` intentionally replaces the two function signatures. To avoid a dispatcher/migration mismatch, stop or disable all pre-0048 dispatcher instances, apply the migration, deploy the token-aware dispatcher, and only then re-enable dispatch. The database grants execute authority only to `developer_api_service`; `PUBLIC` retains no execution grant.

This evidence validates source behavior, a loopback connection reset, and the authoritative PostgreSQL scheduler in a disposable local database. It does **not** demonstrate reachable partner endpoints, certificate validation, remote DNS, staging secrets, target-side replay deduplication, distributed worker deployment, real provider delivery, or staging/production readiness.
